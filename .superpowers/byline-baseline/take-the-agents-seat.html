Take the agent's seat

Half of every prompt we send lives in our head. Read what you wrote the way the agent will, before you hit send.

Ari Mendelow · May 2026

We type "fix it" and hit send. In our head, it's the JSON parsing bug in the v2 deserializer we were swearing at five minutes ago. On the agent's screen, it's two words, in a repo with forty things that could be broken.

The agent picks one. Wrong one. We sigh, think "stupid clanker," and type the clarification we should have typed the first time. We quietly decide the agent doesn't get it.

But that mistake was our fault! Our agent only had the context we gave it, and we only gave it half a prompt.

I call the missing half the ghost prompt: everything that lived in our head and never made the trip. Last night's context. The file we almost touched yesterday. The thing "we discussed". The agent got the words, and we're judging its work against a brief it never saw.

Here's what I do: before I hit send, I put myself in the agent's shoes.

What falls out

Read your prompt as someone whose entire worldview consists of the system prompt, the current conversation, and literally nothing else. A few things usually fall out:

  • The pronoun with no antecedent. "Make it work the way we discussed." Which "it"? Which "way"? If this conversation didn't carry the discussion, the prompt doesn't either.
  • The missing location. "Update the config." There are a hundred config-shaped files. Did you want the agent to spend its time searching, or editing?
  • Last week. "Like we did last week." The agent has no last week. Take the time to either be specific with what you want, or at least tell it where to start looking.
  • The shared frame. "Obviously this is the wrong approach." Obvious by what standard, and where does the agent find it? If you want something to be obvious, you need to ground that obviousness in something.

Where the distrust comes from

Send the half-prompt, and the agent will fill in the gaps, make assumptions using its judgment, and probably do the wrong thing. Correct it, and it ships a different wrong thing. By the third pass you've spent more time correcting than it would have taken to say what you meant, and a quiet thought forms: this agent isn't very good.

The distrust sticks to the agent, because it's the part you can see. Then the distrust feeds everything I wrote about in Trust the Fucking Agent: we stop letting the agent finish, we narrate every tool call, and we end up doing the thinking and letting it type.

We'd hate it done to us. Think of the worst message you ever got from a busy colleague: "hey can you do that thing we talked about, thx." No thread, no link. You guessed, guessed wrong, and both of you were annoyed. That's the prompt we send our agents every day.

Two halves

Trust the Fucking Agent was about trust. This one's about saying what you mean. If you trust the agent and the brief is vague, it flounders, and the floundering confirms your distrust. If the brief is clear and you don't trust it, you end up micromanaging. You want both.

Be direct

Agents are fine with direct! Skip the reassurance, skip phrasing every request as a question, and say exactly what you want.

"Add a unit test for the parser's empty-input case in src/parser/__tests__/parser.test.ts; assert it returns null and logs a warning" already did the work of imagining what the agent needs to know. "can you maybe add a test for the parser? thanks!" is polite, and it leaves the imagining to the agent. And by saying "maybe," we made it optional, so it might just decide to do nothing.

The agent is going to live by what you write. Read it first.

For the trust half, see Trust the Fucking Agent. The design idea behind this is Agent Experience. For a real design conversation from the agent's seat, see The work spoke back.
